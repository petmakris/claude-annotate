# claude-annotate

Run the tests with:

    uv run -q --with-requirements requirements-test.txt python -m pytest skills fleet/tests -q

`requirements-test.txt` pins the test tooling for the pre-push hook and this command alike: pytest, pytest-xdist and aiohttp. The suite runs about 2,700 tests (the fleet plugin's 200 included) in about 50 seconds, on 4 workers (`pytest.ini`). For one file, name it instead of `skills fleet/tests`. Add `-n 0` to run serially.

The suite has no browser tests and starts no daemon: no test drives Chromium, and none needs webcompanion running. Keep it that way. A few tests run the page's JavaScript under node and skip without it. `skills/stage/tests/stage_page.py` and `skills/talk/tests/call_page.py` run the real `stage.js` and `call.js` under node on a small DOM (`skills/_shared/tests/dom_shim.mjs`), for page logic only: every box measures 0, so nothing about layout can be checked there.

A green suite does not show that the tests guard the code. `/audit-tests` (`tools/audit_tests.py`) plants small bugs in the lines changed since its last run and reports each one no test fails on, plus flaky tests and tests that run exactly the same lines as another. When planting a bug by hand to watch a new test fail, set `PYTHONDONTWRITEBYTECODE=1`: a file restored within the same second at the same size otherwise runs the planted bug again from Python's cache (`~/.cache/pycache`).

The repo has no GitHub workflows, so nothing checks a push on GitHub. `.githooks/pre-push` is the only gate: it runs the suite with an empty `HOME` so no daemon config of yours is reachable, after compiling and collecting it under Python 3.9, and blocks the push if anything fails. It runs the full suite under one Python only. `/audit-failing-tests`, typed by hand, runs it under Python 3.9 and the newest Python in a clean worktree, then fixes and pushes what fails. A fresh clone enables it with:

    git config core.hooksPath .githooks

The stage's rules (`skills/stage/SKILL.md`, "What the stage keeps true") are checked on compiled frames by `stage_rule_breaks` in `skills/talk/tests/helpers.py`: call it on any reply a new test compiles. The scene compiler names what is being said in every frame (`cur`); the page draws that and never works it out itself. A saved scene from before `cur` is the one exception: `settled()` in `skills/stage/static/scene.js` gives its frames today's arrow rule as the view arrives, and `beingSaid()` guesses its part being said.

A board keeps one scene per answer that stepped it (`scenes`, keyed by the answer number as a string; `scene` is the one of the answer that last put the board up, absent when that answer had none). In `stage.js` read a view's scene through `sceneOf(v)` or `painted(v)`, never `v.body.scene`, so a replayed answer steps its own frames. Talk numbers an answer by the Claude entries before it, so a test that splits two replies must `call.add("claude", ...)` between them, or both get the same number.

The stage demo's change board (`skills/talk/demo.md`, "Cells and the current one") points at line numbers of `skills/stage/static/scene.js` against an old revision. An edit to that file above those lines moves them: re-point the demo in the same change (`test_the_demos_change_board_points_at_the_lines_it_talks_about` in `skills/talk/tests/test_demo.py` fails until you do, and `/audit-demo` checks the rest).

On the call page every play the reader starts (Play, Space, a tapped word, the conversation's ▶, a spoken "go on", the media keys) goes through `readerPlays()` in `skills/talk/static/call.js`, which resends the whole picture and leaves following as it is: a board the reader picked stays in front. A new way to start playback must call it too; an automatic play (a new answer, a held answer picking up after the user spoke) must not, so its answer's `stage:answer` turns following back on. Only a play of the board in front (Play on a board the voice is not on, Play from here on a step) also calls `followAgain()`. Otherwise following comes back with the stage's Follow the voice button, the gear's switch, or the next answer.

A page is a board of an answer when the answer brings it in with `[[show page: <file in --code, address or session:kind/slug> | Title]]`: it gets a chip and a front cue like any board. A page put up with `stage.py show` during a call opens behind and has no cue, so the voice can never front it; `stage.show` with an owner replaces such a hand-put copy of the same page.

A scene (`[[show scene | T]]` HTML `[[/show]]`) is an answer's own page, revealed part by part: `model.scene_source` reads its `data-part` elements (refusing scripts, handlers and `javascript:` links), `scene.parts_model` makes them keys (`part:<id>`), and the stage keys them for `applyFrame` after DOMPurify (`paintScene`). With no verbs a scene still steps: `auto_steps` steps any scene of two or more parts, and a part no sentence names rides in with its parent. An answer with a front cue is "staged": the call page folds its text to one line and sends each sentence as `stage:caption`, which the stage shows as a bubble under the scene part being said, else as a bar. Design: `docs/superpowers/specs/2026-10-13-talk-answers-are-scenes-design.md`.

The call page reads every answer on the stage (`paintReader` in `call.js`, `#reader` over the stage frame): each sentence appears as it is said and the word being said is lit (`now-word`), a tap on a word plays from there. When the voice reaches a board's front cue the board takes the stage and the reader becomes one strip under it with the sentence being said (`reader strip`); at rest an answer with a board shows the board, and a board the reader picked by hand (following off) stays in front. The stage gets no caption any more, and every answer folds to one line in the panel. Scenes and stops are retired from talk's guide (`skills/talk/SKILL.md`, "No scenes and no stops") and from the demo; their code still runs for saved boards and for a session that writes the tags.

A scene is written as a slide (`<div class="slide">` with a `kicker` and an `h1.title` that states the claim) built from forms in `stage.css`: `flow` and `vs` of `node`s (the arrow or "vs" is the `::before` of each node after the first, shown only with both ends), `stack` of `layer`s, `tiles`, `hero`/`num`, `callout`, `chip`, `tag`, with `data-tone` blue, red, green or amber. A top-level card not said yet is a dashed slot with no words; a part inside a part is `display:none` until said and rises in on a forward step (`s-play`). With no pointed focus, `s-on` dims the parts shown before the one being said. On a slide the caption is a bar across the foot (`caption bar sub`), never a bubble. `model.scene_warnings` turns a part over 16 words, or a scene with no slide, into a `board:` line; it never refuses a scene.

A stop (`[[check]]`, `[[guess: q | a | *b]]`, `[[say back: q]]`, `[[deeper]]`) is a cue `{at, kind: "stop", stop}` with no view: `talk.parse_stop` reads it, its question is put into the spoken text with the cue after it, and no stop question names a scene part (`compile_scenes` blanks them, so a guess never gives its answer away). On the call page `checkStop` pauses the voice at `stopTime` (just after the question's last word), `stopped` holds the stop it waits at, and `heldAt` keeps the stage from running past a stop not yet passed. `stopped` is set before the pause, since a pause paints the stage. The card is on the stage (`stage:stop`, answered with `stage:pick`) for a staged answer, else in the panel (`#stopcard`). A guess pick goes to `/api/pick` and rides on the next turn as `picks`; a say back answer carries `answering`. Design: `docs/superpowers/specs/2026-10-13-talk-stops-asks-and-sandbox-design.md`.

On a scene the stage takes questions (`tapScene` in `stage.js`): a tap on a part shown opens its popup (`.spop`) with Ask about this, which posts `stage:ask` so the call page pauses and starts the text field with `About "<part>": ` (`askAbout`), and Play from here (`playKey`, which also serves a sequence step). A `<dfn title>` shows its meaning, and `captionWords` makes the same term tappable in the caption.

A scene with a `<script>` or an `on…` handler is `sandboxed` (`model.scene_source`; a `javascript:` link is still refused, and script or style text names no part). The stage runs it in `<iframe sandbox="allow-scripts">` with no same origin and a policy of `default-src 'none'` (`paintSandbox`): the stage's stylesheet goes in inline and its fonts as `data:` URLs, since the frame's opaque origin cannot fetch them. `SANDBOX_SHIM`, put in first, keys its parts and applies the `scene:frame` messages `paintFrame` posts (show, focus, cur); it says `scene:ready` and gets the last frame again. Its caption is a bar, and it has no part popup.

The stage draws no Mermaid, and nothing vendors it. A Mermaid body is turned into a JSON spec before it reaches the page: `model.mermaid_source` for `stage.py show diagram:-` (a graph or state diagram becomes a flowchart, a `sequenceDiagram` a sequence) and `Board.from_mermaid` in `talk.py` for a call (a graph or state diagram only). A view of format `diagram` saved before that shows its source (`renderInline` in `stage.js`).

A before/after sequence (`compare: {before, after}`) is two lane boards side by side, never one merged diagram. `skills/stage/compare.py` lines the sides up like a split diff: it pairs steps (by id, else label and arrow), and its spec has one step per row holding the `before` and `after` step, with a gap where a side has none. `renderCompare` in `lanes.js` draws each side as its own lanes board from that row list (`sideSpec`), keyed by the row so a frame lights both, and `syncSides` gives each row the taller side's height so the two stay level. Design: `docs/superpowers/specs/2026-11-10-side-by-side-sequence-compare-design.md`.

The map (`skills/stage/static/map.js`) places its parts once per board size, with room round each for the larger card it becomes when said, and picks its layout (`data-layout`: `ring`, `across`, `down`) by what fits. When the card being said changes, only the arrows and labels are redrawn.

An architecture map on the stage (`[[show map | T]]`, `stage.py show map:-`) is drawn on the server: `model.visual_source` runs `map_svg.render(spec, uid, keyed=True)` and keeps the SVG as the source's `svg`, since the map is measured and routed in Python. The page puts it in through DOMPurify's SVG profile (`paintVzMap` in `stage.js`), styled by `vz.css`. Its keys (`scene.map_model`) are `box:<id>`, `zone:<i>`, `edge:<from>-><to>#<n>` for a structure arrow and `route:<r>` for a step of its route; `layoutVzMap` puts the map in route mode while a frame before the rest shows a route step. With no verbs a map follows its route only when a sentence or a point names a step of it (`auto_steps`), and `[[all]]` never starts the route.

The lanes (`skills/stage/static/lanes.js`) are drawn in the look of `sequence_svg` (four tones, actor heads with their role, a chip on each call, check badges, phases as bands, an outcome box), but stay HTML laid out in the page: they fit any board width, wrap and measure their words, and keep the popups, folding, following an actor and activation bars that `sequence_svg` does not draw. A look changed in one should be changed in the other. They draw a sequence whole, the steps not said yet faint, and draw the board again after every frame: `paint()` rebuilds the rows and gives each keyed element back the classes the frame set (`k-hidden`, `k-focus`), so a class put on a row from outside does not survive the next frame. Each step is one keyed row (`step:<id>`) holding its own arrow, so the scene engine still shows and lights it as one element. Lifelines, boxes (`groups`) and activation bars (from a call to its `reply_to`) are drawn under the rows in one SVG. A row whose words wrap is measured and the board drawn once more (`measure()`); under the node harness nothing measures, so rows keep their base sizes there. A step's popup reads its source lines from the view's `refs`, which `model.step_refs` reads from the code folder when the board is made (talk's `Board.add_refs`, or `stage.py show sequence:-`); Play from here posts `stage:play` and the call page plays from that frame's cue through `playFrom()`, which follows the voice again with `followAgain()`.

A `map` or `sequence` part on the annotate page is stored as the vz player fragment (`render.py`, `visuals/player.py`), drawn at its own size with its title band cut off because the part's heading carries the title; `script-blocks.js` boots the players on every `annotate:rendered`, and Share puts each drawing back to the whole picture with no controls.

The annotate page never shows a block: a block renders as part of one document (`createBlockSection`), an authored title is an `h2` (`visibleTitle`), folding goes by heading (`fold-groups.js`), and every comment opens in the one floating window (`comment-window.js`). Text the reader sees says "part", never "section" or "block".

The canvas viewer (`skills/canvas`, `tools/canvas.py`) is one template for every screenshot canvas: an app's journeys build theirs by running `tools/canvas.py build` from this checkout (`$CLAUDE_ANNOTATE_HOME`), so a change here reaches them at their next build; nothing vendors the page any more. The page builds itself from its JSON data, so the template must stay data-free. What changed since an earlier capture (`changes`, a board's `change`, a shot's `previous` and `diff`) is computed by the project (the project's own compare step); the viewer only draws it. Comments exist only on a canvas with a `session`: the build finds or makes that webcompanion session and registers the folder as its page, and the page keeps every comment as an op log in the session's threads (one thread per board), folded by `canvas-store.js`. `skills/journey/store.py` is the same fold in Python for the journey tool: change both together; `skills/journey/tests/test_journey.py` runs both on the same cases. `canvas-session.js` holds the session's API, its stream, Claude's state and Re-run. `canvas-math.js` and `canvas-store.js` are tested under node; `canvas-page.js`, `canvas-session.js` and `canvas-comments.js` need a browser and have no tests here.

`/journey` (`skills/journey`) is one Claude session per app answering that app's journey canvas, on the host named in your journey config only. The apps are data: your own `~/.config/claude-annotate/journey/apps.json` (kept outside the repo; `JOURNEY_APPS` names another), else the generic `skills/journey/apps.example.json` (where the journey runs, canvas folder, how features are listed and run, where results land). Your machine's settings sit beside it in `config.json` (`JOURNEY_CONFIG`): `host`, `machine`, `home` (the session home), `tooling_home`, `cli` (relative to `home`), `cli_probe` and `sessions_file`; `journey.py` documents each. A journey runs in any sandbox of the app; there is no journey sandbox. Re-run runs the app CLI (`{cli}` in `run`) from the session home, which picks the sandbox the canvas was captured on, else the app's only one, and never makes one. `place()` in `journey.py` reads that sandbox's folder from the canvas's `source.json`. With a `cli_probe` configured, `journey_cli()` falls back to the CLI of the canvas's sandbox, or refuses, when the session home's CLI lacks the probe's needle: an older CLI would make a permanent journey sandbox again. A new journey app is a new entry in the apps file, a session line for it in the file `sessions_file` names, and a doorman restart. `journey.py doorman` runs as the systemd user unit `journey-doorman` (`journey.py install-doorman`) and wakes an app's session headless when an event waits and nobody listens; it runs the checkout's file, so restart the unit after changing `journey.py`. The tests pin `JOURNEY_CONFIG` and `JOURNEY_APPS` to the example (`skills/journey/tests/__init__.py`), so your own files never reach them.

The `fleet` plugin (`fleet/`, a third plugin in the marketplace with `source: "./fleet"`) is separate from the other two: its own `plugin.json`, its own `hooks/hooks.json` and nothing imported from `skills/`. `fleet/fleet.py` is a stdlib-only CLI for Python 3.9+ that joins Claude Code sessions into a fleet and posts messages straight into a member's inbox socket (the `CLAUDE_CODE_MESSAGING_SOCKET` the member exported, stored at join), with no model on the sending side. Design and plan: `docs/superpowers/specs/2026-11-13-fleet-plugin-design.md` and `docs/superpowers/plans/2026-11-13-fleet-plugin.md`. The store is `$FLEET_HOME` (default `~/.claude/fleet`, made 0700; `fleet.db`, `ui.json` and `hooks.log` are 0600, tightened on open if looser) `/fleet.db`; tests set `FLEET_HOME` and `FLEET_SESSIONS_DIR` to temp dirs and never read the real sessions dir, using real sleeping processes as fake sessions and listener threads as fake inboxes, and one fake `claude` (`install_claude_stub`: `agents --json` lists the fake sessions, `--bg`, `stop`, `rm` and the headless `-p` answer) as `FLEET_CLAUDE_BIN` (`fleet/tests/fleet_testkit.py`; no `conftest.py` there, since the repo's other `tests` folders are packages). The repo is public: no machine, host or company names in the fleet code, tests or docs. A session that skips permissions holds inbound messages unless `crossSessionInbound` is `accept`; `fleet spawn` and `respawn` start sessions with it set, and `fleet join` checks nothing about settings (it read undocumented settings files and misjudged them). **One trust domain.** Every member can tell every other member to act, as the user would, so a member that reads untrusted text (a web page, a mail, a log, another repository's files) can be talked into telling the rest. Join only sessions you would trust with each other's tools, and treat what a member relays from outside as untrusted data; the wrapper's text is escaped (`<`, `>` and `&` in a body become `&lt;`, `&gt;`, `&amp;`) so a body cannot close the `cross-session-message` tag and forge a sender, but nothing stops a member from saying it. The hooks act only when `FLEET_JOIN_NAME` is set (SessionStart) or a store exists (SessionEnd). Across machines (`$FLEET_HOME/machines.json`, slice 3) every remote verb is `ssh <host> <python> <fleet.py> <verb>`; a message is stored on the target's machine by the internal verbs `_deliver` and `_answer` (JSON on stdin), a thread id is `t` plus hex (never all digits, which `thread` would read as a message id), and the tests put a fake `ssh` on `PATH` that runs the CLI with another `FLEET_HOME` per host (`World.host`, `World.link` in `fleet_testkit.py`). A subagent's Bash inherits its parent's `CLAUDE_CODE_SESSION_ID` and messaging socket, so any `fleet` command run there acts as the parent session: manual checks must use sessions you started (`claude --bg`), whose environment is set by `--settings '{"env":{...}}'`, since `claude --bg` hands the process to a daemon and shell variables such as `FLEET_JOIN_NAME` do not reach it. `fleet ui [--port N] [--host H]` (slice 4) serves a page from `fleet/ui/` (`index.html`, `app.css`, `app.js`, no external assets) and `/api/members`, `/api/todos`, `/api/threads`; they fan out like `ls` (the internal verb `_threads` gives a remote machine's threads, and a message stored on both machines shows once), an unreachable machine is a `notices` entry, the page itself shows members and the backlog (a to-do's notes behind a closed Notes toggle) and no longer shows threads, which stay in the API and `fleet thread`, answers are cached for 3 s, and the page polls every 5 s while visible. Port and host come from `$FLEET_HOME/ui.json` (default 127.0.0.1:8797). **The page needs a token.** It is `token` in `ui.json` when set, else the owner's shared password (the first line of `~/.config/shared-token`, moved by `FLEET_SHARED_TOKEN_FILE`, which the tests point at a temp file), else a `secrets.token_urlsafe` value made on first use and written to `ui.json` (0600, other keys kept); every request but `/login` needs it as the `fleet_ui` cookie (`HttpOnly; SameSite=Strict`, plus `Secure` when `X-Forwarded-Proto` says https, which can only add the flag) or as `Authorization: Bearer`, else 401 with a hint. `fleet ui url` prints `/login?t=<token>` (an https link on the first non-loopback entry of `hosts`, else the loopback address): opening it sets the cookie and redirects to `/`, so the token never stays in the address bar. Without the cookie, `/` is a sign-in form that posts `password` to `/login`, which sets the same cookie (a wrong one waits a second and shows the form again). The server reads the token once at start; restart it after changing `ui.json`. The Host allow-list applies to every request, static files and the read-only API included (history, inbox and writes additionally need a loopback bind). Each request closes the store connections it opened (`db_scope`), a handler socket times out after 30 s, and `test_serving_many_requests_leaves_the_open_descriptor_count_flat` holds the descriptor count flat: without that the long-running service ran out of descriptors (`Errno 24`) because connections waited for the garbage collector. Session history (slice 5) lives in `fleet/fleet_history.py` (stdlib, no fleet imports; `fleet.py` wraps it) and the `conversations` table of the same store. `hooks/record.sh` (SessionStart, Stop, SessionEnd) runs `fleet hook-record` for every session, joined or not: it reads only the first 256 KB (or, when that holds no newline, up to the end of the first line) and last 1 MB of the transcript, never calls a model, logs errors to `$FLEET_HOME/hooks.log` and always exits 0; it skips a session when `FLEET_NO_RECORD` is set, which every headless call of the plugin sets. A name is kept per kind (`name_custom`, `name_ai`, `name_agent`, each the newest in the transcript) and shown as manual rename, then custom, ai, agent. `fleet history ls|show|rename|delete|resume|ask|describe|search|import`: `ask`, `describe` and `search` are one `claude -p --tools ""` call each (no tools, since the prompt holds transcript text that may carry instructions) through `FLEET_CLAUDE_BIN` (models `FLEET_DESCRIBE_MODEL` haiku, `FLEET_ASK_MODEL` sonnet, `FLEET_DESCRIBE_PAUSE` seconds between describe calls); `describe` runs only on request. `import <db> [--descriptions <db>]` reads another store's `conversations` (and `digests`) read-only. History is this machine's only; it does not fan out. The page writes through POSTs under `/api/` (History, and the control writes below): the server refuses the History API and every write unless it listens on loopback, the Host is a loopback name (or listed in `hosts` of `ui.json`, for a proxy), and a POST has an Origin equal to Host, no cross-site `Sec-Fetch-Site`, and a JSON content type. `fleet/tests/test_fleet_history.py` uses a stub `claude` (`STUB` there) and made-up transcripts. A test that runs a command as another machine's session moves `FLEET_HOME` in the shared process; call `world.here_env()` before asking the server. `fleet spawn` and `fleet todo spawn` run `claude --bg` (`FLEET_CLAUDE_BIN` replaces the binary, `FLEET_CLAUDE_ARGS` adds arguments such as `--plugin-dir <fleet folder>` for a scratch session); a spawned to-do's prompt starts `/fleet todo claim <id>`, and the to-do is reserved for the spawned name until it claims. **Documented sources only (hardening, 13 November 2026).** Liveness, kind, name and the id of a started session come from `claude agents --json` (`is_alive` asks it; the pid and start time recorded at join, checked against the undocumented `~/.claude/sessions/<pid>.json`, are only the fallback when that command cannot run); a session's own id and socket come from `CLAUDE_CODE_SESSION_ID` and `CLAUDE_CODE_MESSAGING_SOCKET`; the `.key` peer token is never read and no auth line is sent (optional on macOS and Linux per the docs, so native Windows is not supported); `fleet spawn` and `respawn` look the new session up by name in `claude agents --json` (`FLEET_FIND_WAIT` seconds, default 10) instead of parsing `--bg` output. **Delivery is confirmed, not assumed.** The envelope the socket reads (`msgV`, `msg_id`, `priority`, the `cross-session-message` wrapper) is undocumented, so every post ends with `(delivery check: fleet-ref-<message id>-<nonce>)` and a message counts as delivered once that marker shows in the target's transcript (`transcript_path`, recorded at join from the hook input or from the history row). `messages.delivery` is `delivered` (written, no transcript known to check), `confirmed`, `unconfirmed` (written, marker not seen within `FLEET_CONFIRM_WAIT`, default 3 s) or `failed`; an `unconfirmed` message starts a detached `fleet _confirm <id>` that keeps looking for `FLEET_CONFIRM_WINDOW` seconds (90), then falls back to the documented path, a headless `claude -p` through `FLEET_CLAUDE_BIN` with `FLEET_NO_RECORD` set and `--allowedTools SendMessage,ListAgents` (skipped while `claude agents --json` says the target is busy, for up to `FLEET_BUSY_WINDOW` seconds, 300, since its turn will read the queued message; either marker confirms) that is asked to send the same text (new marker) to the member by name and id, looks again for `FLEET_FALLBACK_WINDOW` seconds (60), and marks the message `failed` with one line in the user's inbox and in `hooks.log` when that fails too. An explicit refusal in the socket's reply (JSON with `error`, `ok:false` or an error-like `type`; the docs name no reply format) is a failed post with its reason.
